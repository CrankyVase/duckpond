# Agent and chat harness changes

Source changes only. The application, build, tests, browser, models and containers
were not started for this work, and no service was restarted or deployed.

## Coding workbench

- Validates tool arguments against the tools offered for the run before dispatch.
- Records tool outcomes and durations, with recovery guidance and bounded retries
  for unchanged failing calls. Permission denials remain authoritative.
- Adds an `update_plan` tool and confirmed plan events for live runs and replay.
- Shows a progress summary, plan checklist, correlated tool cards, command output
  and recorded verification activity. Successful commands are reported as
  commands, not automatically classified as passing tests.
- Adds per-conversation `agent_execution`: `execute` (existing default) or `edit`.
  Edit-only runs allow source inspection and edits, and block execution tools,
  browser checks, media generation and GitHub publishing. Initial turn tool
  selection and backend dispatch both enforce the mode. Standalone run requests
  accept the same setting.
- Improves bounded source search and project orientation: file-path searches,
  case sensitivity, nearby lines, scripts, dependency versions and nested
  instruction locations.

## Normal chat

- Routes offered GitHub reads through the normal tool loop without creating a
  coding workspace. Unoffered tools are rejected before dispatch.
- Validates JSON and schemas, counts malformed calls toward turn budgets, caches
  settled results to avoid duplicate image/widget/memory actions, and ends
  repeated-failure loops with a tool-free final response.
- Pure image batches respond to every tool-call ID while limiting actual image
  jobs to two per turn. Empty image output and empty model answers are explicit.
- Preserves direct page-read traces, cancellation between batched actions, and
  reported token usage across rounds. Final context counting uses the actual
  tool transcript.
- Restricts speculative search/page reads to tools offered for the turn, and
  resets draft text when retrying an unsupported tool template.
- Keeps reconnect snapshots authoritative after text resets and resumes partial
  tool argument buffers. New tool rounds clear old buffers.
- Distinguishes reply delivery from worker settlement so new messages and
  deployment cannot race post-delivery cleanup.
- Makes search traces keyboard accessible with page-read badges and expandable
  results.

Regression test source accompanies the harness, job lifecycle and search changes. Runtime
behavior and frontend rendering still need verification when running code is
permitted.

When execution is permitted, `server` provides `npm run test:harness` and
`npm run test:workspace`; the Svelte production build and workbench browser
checks should follow. Those commands were not run during this edit-only session.

workspace, tools and recent conversations, keeps account controls outside the
scrolling list, and separates the model controls from runtime meters.

The conversation and composer share gutters. Messages expose author labels,
clearer action groups and more readable code blocks. Optional response settings
open in a bounded, dismissible dialog rather than pushing the draft controls around.

Static review and whitespace checks only. This layout has not been rendered or

## Backend efficiency and tool visibility follow-up

This follow-up remains source-only. No services, containers, builds, tests,
models or benchmarks were started. Existing model files, sampling settings,
32K local context, Q8 KV precision and saved tuning choices are preserved.
There is no newly measured TPS improvement to report.

Inference changes:

- Identical exact-tokenizer requests share pending work and a short-lived,
  bounded cache. Completed entries retain only request digests and token counts.
  Changed prompts/models get separate counts; failed/unknown results are not
  cached. Registry/load/unload changes invalidate cached counts, including
  in-flight cache writes. A stopped caller leaves other subscribers working;
  when the final subscriber stops, the shared tokenizer request is cancelled.
- Tokenizer work participates in model activity tracking. Explicit model
  loads/unloads report a busy worker while a request is active instead of
  attempting eviction. Independent Fedora/Windows workers remain separate.
- Local streaming stops requesting timing objects for every token. Text/tool
  fragments still stream; final native throughput remains authoritative, and
  parsed prompt-progress events keep the stream deadline current. Stream
  readers release upstream work even when a consumer callback fails.
- Post-reply memory extraction respects Stop, including embedding requests.
  An explicitly disabled embedding pipeline skips the otherwise wasted model
  extraction pass and its estimated usage entry; no candidates could be saved
  by that disabled pipeline previously.
- Validated per-model prompt-batch controls use existing native defaults.
  The manually invoked batch comparison adds exact-tokenized near-32K recall
  checks and does not change saved profiles. These options follow the
  [pinned llama.cpp documentation](https://raw.githubusercontent.com/ggml-org/llama.cpp/b11146/tools/server/README.md).

Hardware tuning still needs later measurement on the actual worker. Compare
uncached prompt throughput, sustained generation speed, time to first token,
recall, generated code/text and RAM/VRAM headroom together. Increasing thread
counts, physical batches or GPU allocation without measurements can slow a
partially offloaded model or crowd out Windows applications. No new speculative
mode, lower precision, smaller context or increased slot count was enabled.

Source regression coverage includes exact token-count reuse/invalidation and
final stream timing retention. `server` exposes `npm run test:inference` for a
later permitted verification pass; it was not run here.

Sandbox and search changes:

- Sandbox command transport drains output into bounded byte buffers instead of
  collecting megabytes until the child CLI fails. Commands accept an explicit
  project working directory, including folders with spaces; package caches
  live in the existing persistent sandbox home volume.
- Concurrent sandbox starts share startup work. Active commands and agent runs
  are excluded from idle stopping. Stop reaches command process groups and
  waits for bounded cleanup; inability to confirm cleanup is reported with the
  command output and metadata. Container timeout remains a fallback.
- Validated independent web searches/page reads overlap with a concurrency cap
  of three. Transcript result ordering, search depth and result content are
  preserved. Unclaimed speculative reads are bounded and cancelled between
  rounds and at turn completion.
- Slow primary searches may start a backup request after 1.5 seconds, while the
  original primary deadline and primary-result preference stay intact. This
  reduces sequential fallback waiting but can add a backup request even when
  the slow primary eventually succeeds; unused backup work is cancelled.
- Search updates carry query identities and status/error fields through live
  and reconnect snapshots. Failed page reads remain visible without becoming
  successful citations.

The UI shows query errors, read states, pending/empty searches and expandable
snippets with touch/keyboard controls. Tool cards expose input previews,
duration, saved receipts and cancelled/failed outcomes. Replay history reports
loading/reconnection issues and updates to the final run status. These layouts
use the existing palette and adapt to narrow conversation panes.

Additional test source covers bounded command output/cancellation, read-ahead
limits and primary/backup search behavior. The later verification entry points
are `npm run test:workspace`, `npm run test:search`, `npm run test:inference`, the
bridge lifecycle tests and the frontend build/browser checks. None was run in
this pass.
